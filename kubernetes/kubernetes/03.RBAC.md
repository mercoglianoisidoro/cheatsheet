# Role Base Access Control

## Intro

To perform each action, 3 steps:
1. **Authentication**: provides the identity of the caller
2. **Authorization** (ABAC or RBAC): check if the user has permission to run that action
3. **Admission Control**: check the actual content of the object being created and validate them before admitting the request.

The 3 step use TLS: they need a certificate.

### Authentication

In short: made by certificates, token or basic auth (user/pass).
Interestingly enough, Kubernetes does not have a built-in identity store: it integrates other identity sources.
So users are not created by API.

The form of Authentication are set by init script (option command like --basic-auth-file)

Here some provider supported (different plug-ins):
- HTTP Basic Authentication (deprecated)
- x509 client certificates
- Static token files on the host
- Cloud authentication providers
- Authentication webhooks

#### Kubectl

Kubectl is able to connect to k8s because it use a client certificate that carry a token with which to authenticate.


### Identity

Every request is associated with an identity (Requests with no identity are associated with the system:unauthenticated).

Here the various identity types.

#### User
Users cannot be added via an API call, any user that presents a valid certificate signed by the cluster's certificate authority (CA) is considered authenticated.

#### Groups
Groups are not a managed resources in k8s => their name is name is just an arbitrary name.

#### Build-in groups
The build-in groups are different from groups: they are managed by the API server and cannot be modified. 
They are system:
- system:authenticated: users who are successfully authenticated
- system: none of the authentication plugins can validate the request
- system:masters: super users intended to have access to everything
 
#### Service account
If the request originates from a machine, it must have a Service Account, and its credentials must be stored as a Secret in Kubernetes.
Service account are users managed by the Kubernetes API and are generally associated with components running inside the cluster: they let a process inside a pod to perform action in the cluster.

Service accounts, tied to a set of credentials stored as Secrets, can be mounted into pods. By default a default SA (and its token) is associate to each pod: this default behaviour can be disabled (automountServiceAccountToken: false).

Service Accounts are namespace-scoped resources.

More info: https://kubernetes.io/docs/tasks/configure-pod-container/configure-service-account/

Attach a pod to a service account:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: name
spec:
  serviceAccountName: SANAME
  containers:
  - image: nginx
  dnsPolicy: ClusterFirst
  restartPolicy: Always

```

### Authorization

3 modes:
- ABAC (Attribute Based Access Control, it needs the autothentication policy file, a json file)
- RBAC (Role Based Access Control, the default one)
- Webhook

(passed to API server startup options:
 --authorization-mode = ABAC, RBAC, Webhook, Alway Deny, Always Allow)



## RBAC

### Role and RoleBinding

**Roles** = a group of rules. They affect **a single namespace**, ant they are scoped to a particular resource in k9s (ex pod).
Rules = operation which can act upon API group
By a binding they apply to:
- User (which doesn't exist as API object)
- Service Account
- Groups

In other words:
A **role** (set of abstract capabilities) can be assigned to one or more identity through a **role binding**.
Role binding applies to 2 pairs of related resources:
- Role and RoleBinding
- ClusterRole and ClusterRoleBinding


**Verbs for Kubernetes roles**: roughly = HTTP methods

| Verb     | HTTP method | Description                                          |
| :------- | :---------- | :--------------------------------------------------- |
| `create` | `POST`      | Create a new resource.                               |
| `get`    | `GET`       | Get a resource.                                      |
| `list`   | `GET`       | List a collection of resources.                      |
| `patch`  | `PATCH`     | Modify an existing resource via a partial change.    |
| `update` | `PUT`       | Modify an existing resource via a complete object.   |
| `watch`  | `GET`       | Watch for streaming updates to a resource.           |
| `proxy`  | `GET`       | Connect to resource via a streaming WebSocket proxy. |
| `delete` | `DELETE`    | Delete an existing resource.                         |



#### examples

**Create a role by command line**:

```bash
kubectl create role pod-reader --verb=get,list,watch --resource=pods -o yaml

```

**Role manifest** (from kubernetes.io)
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
- apiGroups: [""] # "" indicates the core API group
  resources: ["pods"]
  verbs: ["get", "watch", "list"]
```


**Create a role by command line**:

```bash
kubectl create rolebinding pod-reader-binding --role=pod-reader --user=jane

```


**RoleBinding manifest** (from kubernetes.io)
```yaml
apiVersion: rbac.authorization.k8s.io/v1
# This role binding allows "jane" to read pods in the "default" namespace.
# You need to already have a Role named "pod-reader" in that namespace.
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default
subjects:
# You can specify more than one "subject"
- kind: User
  name: isidoro # "name" is case sensitive
  apiGroup: rbac.authorization.k8s.io
roleRef:
  # "roleRef" specifies the binding to a Role / ClusterRole
  kind: Role #this must be Role or ClusterRole
  name: pod-reader # this must match the name of the Role or ClusterRole you wish to bind to
  apiGroup: rbac.authorization.k8s.io

```

### ClusterRole and ClusterRoleBinding

**clusterrole**: a set of well-known system identities that require a known set of capabilities.

4 are designed for generic end users:
- 'cluster-admin': complete access
- 'admin': access to a complete namespaceThe
- 'edit': allows an end user to modify things in a namespace
- 'view': allows for read-only access to a namespace.


ClusterRole is a non-namespaced resource.

ClusterRoles have several uses. You can use a ClusterRole to define permissions on:

- namespaced resources and be granted within individual namespace(s)
- namespaced resources and be granted across all namespaces
- cluster-scoped resources


**To get them:**

```bash
kubectl get clusterroles
```
or
```bash
kubectl get clusterrolebindings
```



**Attention points:**

1. A certain number of ClusterRoles come directly from the code of the servcer:  modification to these built-in roles are transient.
   To avoid this problem: you need to add the rbac.authorization.kubernetes.io/autoupdate annotation with a value of false to the built-in ClusterRole resource.

2. By default, a cluster role system:unauthenticated is intalled: it allows users to access to the API server’s API discovery endpoint.This could be a bad idea: for cluster exposed on the public internet or an other hostile environment, you should ensure that the --anonymous-auth=false flag is set on your API server.



### ClusterRole VS Roles

If you want to define a role within a namespace, use a Role; if you want to define a role cluster-wide, use a ClusterRole.


### ClusterRole and RoleBinding

When you need to "attach" a resources that is not scope by a namespace to a ClusterRole.

User,Group,or AS   -> RoleBinding -> ClusterRole --> access to Node for example

### Aggregation

Kubernetes RBAC supports aggregation rule to combine multiple roles.

This is achieved by using label selectors.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: edit
  ...
aggregationRule:
  clusterRoleSelectors:
  - matchLabels:
      rbac.authorization.k8s.io/aggregate-to-edit: "true"
...
```



### Groups for Bindings

It’s generally a best practice to use groups to manage the roles that define access to the cluster.

Groups are supplied by authentication providers.

To bind a group to a ClusterRole:

```yaml
...
subjects:
- apiGroup: rbac.authorization.k8s.io
  kind: Group
  name: my-great-groups-name
...
```

## Groups
Groups are used to **logically group together multiple users or service accounts** for the purpose of assigning permissions via RoleBindings or ClusterRoleBindings.
Groups themselves do not define any permissions.

**Groups vs ClusterRoles**: clusterRoles are Kubernetes objects that define a set of permissions that can be performed on specific resources across all namespaces in the cluster.
ClusterRoles do not specify which users/groups get those permissions.

To grant the permissions defined in a ClusterRole to users or groups, you need to create a ClusterRoleBinding that associates the ClusterRole with the desired subjects (users, groups, or service accounts).

**Example**:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
	name: ClusterRoleBindingForDoit
	namespace: default
subjects:
	- kind: Group
	  name: devteam:viewers
	  apiGroup: rbac.authorization.k8s.io
roleRef:
	kind: ClusterRole
	name: view
	apiGroup: rbac.authorization.k8s.io
```

## kubeconfig creation
Let’s start by creating a new certificate-signing request.
Because Kubernetes API is its own certificate authority, it can sign certificates for us, rendering them valid authentication mechanisms for the Kubernetes API.

**Note on csr files.**
A file with a ".csr" extension stands for Certificate Signing Request.
This type of file is used (for example by websites) to authenticate their identity to a Certificate Authority.
When applying for an SSL/TLS certificate, a CSR is generated on the server where the certificate will be installed. The CSR contains information such as the common name (CN), organization (O), organizational unit (OU), city/locality (L), state/county/region (S), country (C), and email address. Additionally, the CSR includes the public key that will be included in the certificate and information about the key type and length.


```bash
# First step, create a private key for the user isidoro
openssl genrsa -out isidoro.key 2048

# create a certificate-signing request specifing the user and group
openssl req -new -key isidoro.key -subj "/CN=isidoro/O=developers" -out isidoro.csr

# create a certificate request
export REQUEST=$(cat isidoro.csr | base64 -w 0)
cat <<EOF >> csr.yaml
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: isidoro
spec:
  groups:
  - developers
  request: $REQUEST
  signerName: kubernetes.io/kube-apiserver-client
  usages:
  - client auth
EOF


# apply and check it's creation
kubectl apply -f csr.yaml
kubectl get csr

# approve it and check it
kubectl certificate approve isidoro
kubectl get csr

# get the result
kubectl get csr isidoro -o jsonpath="{.status.certificate}" | base64 -d > isidoro.crt

# and set the add to conf
kubectl config set-credentials isidoro --client-key=isidoro.key --client-certificate=isidoro.crt --embed-certs
```

then you can create a context and use it


more info:
https://kubernetes.io/docs/reference/access-authn-authz/certificate-signing-requests/#create-certificatesigningrequest
